# ProjectMentor AI 面试准备与简历写法

这份文档用于后端实习面试准备。表达目标是“真实、克制、能解释清楚”，不要把项目包装成成熟线上平台，也不要承诺没有实现的能力。

## 1. 简历写法

可以使用的克制版本：

```text
ProjectMentor AI：面向计算机学生的项目真实性审计与面试准备工具。项目基于 Spring Boot 3 + Vue 3 实现，支持用户登录、项目管理、README 保存、普通项目 ZIP 解析、规则扫描、证据链展示、审计报告、AI 幻觉检测、规则版模拟面试、额度流水和 Docker Compose 本地部署。系统采用“规则扫描 + 证据链 + AI 增强”的设计，AI 服务不可用时可降级为规则版报告，适合作为全栈 MVP 和后端实习项目展示。
```

如果简历篇幅较短，可以压缩成：

```text
基于 Spring Boot 3 + Vue 3 实现项目真实性审计工具，支持 JWT 登录、项目 ZIP 解析、规则扫描、证据链报告、AI 幻觉检测、异步分析任务、Redis 进度缓存和 Docker Compose 部署。
```

重点背诵：

```text
我不会把它描述成成熟线上平台，更准确的说法是：这是一个围绕“项目材料是否能支撑简历和面试表达”的全栈 MVP，重点展示后端业务建模、鉴权、文件解析、异步任务、Redis 缓存、额度流水和 Docker 部署能力。
```

## 2. 项目一句话介绍

ProjectMentor AI 是一个面向计算机学生的项目真实性审计与面试准备工具，通过规则扫描、证据链和 AI 增强，帮助用户识别 README 夸大、AI 回答幻觉、简历风险和面试追问风险。

重点背诵：

```text
这个项目不是单纯让 AI 打分，而是先从 README、配置和代码文件里提取证据，再给出更保守的报告和面试建议。
```

## 3. 面试时怎么讲项目背景

可以这样讲：

```text
我观察到很多同学会用 AI 写 README、润色简历或准备面试，但 AI 经常会把项目描述得过于完整。问题是 README 写得好，不代表代码里真的有对应实现；AI 说可以写进简历，也不代表面试能解释清楚。所以我做了 ProjectMentor AI，把重点放在“项目描述和代码证据是否一致”上。
```

为什么这样设计：

- 学生项目常见问题不是“不会写介绍”，而是“不知道哪些表述有证据支撑”。
- 纯聊天式 AI 容易给出笼统建议，缺少文件和代码依据。
- 规则扫描可以保证基础输出稳定，AI 只作为增强能力。

## 4. 项目核心流程讲解

核心流程：

```text
注册登录
  ↓
创建项目
  ↓
粘贴 README 或上传普通项目 ZIP
  ↓
解析文本文件并过滤无关目录
  ↓
规则扫描 README 和项目文件
  ↓
生成带证据链的审计报告
  ↓
AI 幻觉检测 / 模拟面试追问
```

重点背诵：

```text
用户先把项目材料交给系统，系统不会直接相信 README，而是结合上传文件做规则扫描，再把结论、风险点和证据链组织成报告。
```

为什么这样设计：

- 先创建项目，是为了把 README、文件、报告、任务和面试会话都挂到同一个业务对象下。
- README 和 ZIP 都支持，是为了兼容不同演示场景：轻量演示可以粘贴 README，完整演示可以上传项目 ZIP。
- 报告保留证据链，是为了让用户知道“这句话能不能写进简历”。

## 5. JWT 鉴权怎么讲

登录成功后，后端生成 JWT 返回给前端。前端保存 token，并在后续请求中通过 `Authorization: Bearer <token>` 携带身份信息。

后端通过拦截器处理 `/api/**` 请求，排除注册、登录和健康检查接口。拦截器校验 token 后，从 token 中解析 `userId`，写入当前请求上下文，业务层再通过上下文获取当前用户。

重点背诵：

```text
JWT 在这个项目里主要解决“请求是谁发起的”。后端不是相信前端传来的 userId，而是从 token 中解析当前用户，再在业务查询里带上这个 userId。
```

为什么这样设计：

- 前后端分离项目需要无状态鉴权，JWT 实现简单，适合这个阶段。
- 用户身份由后端从 token 解析，避免前端随意传 `userId`。
- 后续项目、报告、任务和额度都可以统一依赖当前用户上下文。

## 6. userId 数据隔离怎么讲

项目里的核心数据都和用户有关：项目、文件、分析任务、报告、面试会话、额度账户和额度流水。业务接口会基于当前登录用户的 `userId` 查询或校验数据。

例如：

- 查询项目列表时，只查询当前用户的项目。
- 查看项目详情时，会校验项目是否属于当前用户。
- 生成报告前，会先确认项目归属。
- 查看报告时，会通过报告关联的项目继续校验用户归属。

重点背诵：

```text
我的处理原则是：用户不能通过改 URL 里的 projectId 或 reportId 访问别人的数据。所有关键查询都要回到当前登录用户的 userId 做校验。
```

为什么这样设计：

- 项目数据、简历建议和面试记录都属于个人信息，不能跨用户可见。
- 后端校验比前端隐藏按钮更可靠。
- 即使当前只是 MVP，也应该保留基本的数据边界意识。

## 7. ZIP 上传安全怎么讲

ZIP 上传用于让系统读取项目里的 README、配置、代码和 SQL 文件。当前支持普通项目 ZIP，最大 200MB。

主要限制：

- 自动过滤 `.git`、`target`、`node_modules`、`dist`、`build` 等目录。
- 过滤 `.idea`、`.vscode`、`logs` 等和分析无关的目录。
- 拦截绝对路径、盘符路径、`..` 路径和空字节，降低 Zip Slip 风险。
- 只解析常见文本文件，例如 `.md`、`.xml`、`.yml`、`.yaml`、`.properties`、`.java`、`.sql`、`.json`、`Dockerfile`。
- 跳过图片、Office 文档、压缩包、可执行文件、音视频等二进制文件。
- 对单文件大小、保存文本总量和 ZIP entry 数做限制。

重点背诵：

```text
ZIP 上传不是为了保存用户完整代码仓库，而是为了提取能支持审计的核心文本材料。所以我会过滤依赖目录、构建产物和二进制文件，并对路径和大小做限制。
```

为什么这样设计：

- 依赖目录和构建产物体积大，但对判断项目能力帮助有限。
- 二进制文件不适合直接入库，也不适合交给规则扫描。
- 路径校验可以避免压缩包里构造危险路径。

## 8. 规则扫描和证据链怎么讲

规则扫描主要做两件事：

- 根据 README 中的描述识别可能夸大的能力点。
- 在项目文件中查找可以支撑这些能力点的证据。

证据可以来自：

- `pom.xml`、`package.json` 等依赖文件。
- `application.yml`、`Dockerfile`、`docker-compose.yml` 等配置文件。
- Java 代码里的 JWT、Redis、异步任务、Controller、Service、Mapper 等实现线索。
- SQL 初始化脚本和数据库表结构。

重点背诵：

```text
我没有直接让 AI 判断项目好不好，而是先用规则把 README、配置和代码线索对应起来。报告里尽量不只给结论，还会告诉用户结论来自哪些文件或代码证据。
```

为什么这样设计：

- AI 可以总结，但不适合作为唯一判断来源。
- 证据链能帮助用户准备面试追问。
- 规则扫描即使不完美，也比完全依赖 AI 更稳定、可解释。

## 9. AI 增强和 fallback 怎么讲

AI 模块使用 OpenAI-compatible API，可以接 DeepSeek、豆包或 OpenAI 风格接口。AI 的作用是补充表达、组织报告、给出更自然的建议，不负责替代所有规则判断。

当 AI Key 未配置、接口失败或返回格式不稳定时，系统会降级为规则版报告。

重点背诵：

```text
我把 AI 放在增强层，而不是基础层。基础报告由规则扫描保证可用，AI 可用时再做表达补充；AI 不可用时，用户仍然能看到规则版报告。
```

为什么这样设计：

- 外部 AI 服务可能不可用，不能让核心流程完全依赖它。
- AI 输出可能不稳定，需要保留可控的规则结果。
- 对面试项目来说，这样更容易解释系统边界。

## 10. Redis / 异步任务 / 额度系统怎么讲

异步任务：

- 前端发起分析请求后，后端创建分析任务。
- 任务进入后台线程执行，避免接口一直阻塞。
- 前端轮询任务状态和进度。

Redis：

- Redis 用于缓存异步分析任务进度。
- MySQL 仍然保存任务状态，Redis 失败时不应该导致业务完全不可用。

额度系统：

- 新用户注册后获得初始分析额度。
- 生成报告前扣除额度。
- 生成失败时返还额度。
- 通过额度流水记录消耗、返还和管理员加额。

重点背诵：

```text
异步任务解决的是报告生成可能耗时的问题；Redis 解决的是进度读取更轻量的问题；额度流水解决的是每次消耗和返还能被追踪的问题。
```

为什么这样设计：

- 报告生成涉及扫描、AI 调用和落库，不适合让 HTTP 请求长时间等待。
- Redis 适合保存短期进度状态，MySQL 适合保存最终任务状态和报告结果。
- 额度流水让系统具备最基础的运营模型，但当前没有接入真实支付。

## 11. Docker / Nginx / Cloudflare Tunnel 怎么讲

Docker Compose 本地部署包含：

- `mysql`：保存用户、项目、文件、报告、任务和额度数据。
- `redis`：缓存异步任务进度。
- `backend`：Spring Boot 后端服务。
- `frontend`：构建 Vue 前端静态资源。
- `nginx`：提供统一访问入口，并把 `/api` 转发到后端。

Cloudflare Tunnel 的作用是临时把本机前端服务暴露给外部访问，方便发给同学试用。它适合演示和测试，不适合长期正式运营。

重点背诵：

```text
Docker Compose 是为了降低本地演示和部署成本；Nginx 负责统一入口和 API 转发；Cloudflare Tunnel 只是临时试用链路，不是正式部署方案。
```

为什么这样设计：

- Docker Compose 能一次启动 MySQL、Redis、后端、前端和 Nginx，减少环境差异。
- Nginx 让前端访问和后端 API 走同一个入口，演示更直观。
- Cloudflare Tunnel 可以快速给别人试用本机服务，但链接临时、稳定性有限。

## 12. 常见追问题和回答思路

### 为什么不直接把 README 发给 AI 分析？

回答思路：

```text
直接交给 AI 很容易得到比较泛的建议，而且 AI 不一定知道代码里有没有对应实现。我希望先用规则扫描把 README 和项目文件对应起来，再让 AI 做表达增强。这样报告更可解释，也更适合面试准备场景。
```

### 规则扫描会不会误判？

回答思路：

```text
会有误判可能，所以我没有把规则扫描包装成绝对判断。它更像一个初筛工具，用来提示用户哪些表述需要证据。后续可以通过扩充规则库、引入更细的代码解析和用户反馈来改进。
```

### Redis 挂了怎么办？

回答思路：

```text
Redis 当前主要存任务进度，MySQL 仍然保存任务状态和报告结果。理想情况下 Redis 失败不应该影响最终报告生成，只是进度展示会降级或不够实时。
```

### 为什么要做额度系统？

回答思路：

```text
报告生成可能涉及 AI 调用，真实产品里通常需要限制使用次数。当前额度系统没有接入支付，只是实现了账户、消耗、返还和流水，用来展示基础业务闭环。
```

### ZIP 上传为什么不保存所有文件？

回答思路：

```text
这个功能的目标不是代码托管，而是提取审计需要的文本证据。保存所有文件会带来体积、安全和隐私问题，所以只保留 README、配置、代码和 SQL 等核心文本文件。
```

### 这个项目和普通 AI 面试工具有什么区别？

回答思路：

```text
普通 AI 面试工具更多是生成题目和评价回答。ProjectMentor AI 更关注“项目材料本身是否支撑简历表达”，所以会先看 README、配置和代码证据，再做报告和追问。
```

### 如果面试官问项目最大的不足是什么？

回答思路：

```text
当前不足主要有三点：第一，规则库还比较基础；第二，面试追问还是规则版 V1，不够智能；第三，还没有真实线上用户反馈。后续我会优先做 PDF 导出、分享报告、RAG 项目问答和更完善的用户反馈闭环。
```

## 13. 面试表达边界

建议避免这些说法：

- 不使用夸大性能、用户规模或商业成熟度的表达。
- 不说“完全避免 AI 幻觉”，只说“识别部分过度鼓励和缺少证据的表达”。
- 不说“完整智能面试系统”，只说“规则版模拟面试和追问原型”。
- 不说“正式支付系统”，只说“额度账户和流水原型”。

可以采用这些说法：

- “当前是可试用版本。”
- “核心流程已经打通。”
- “规则库和面试问题库还需要继续扩展。”
- “AI 是增强层，规则扫描是兜底能力。”
- “更适合作为后端实习项目展示，而不是成熟商业产品。”
